## 1. Purpose

LCC WFM is a workforce-management web application for a bilingual call-center operation run by **Infinity** (a staffing vendor) on behalf of **LCC (Legal Conversion Center)**. Supervisors and operations coordinators use it daily to manage the live call floor: agent profiles and schedules, overtime shifts (including an open-shift job board), attendance/adherence tracking driven by Five9 CSV uploads, Erlang-C staffing forecasts, an approval-based request system (vacation, VTO, LOA, schedule changes, coding requests, shift claims, cancellations), and the money side — weekly billing from Infinity to LCC in USD and agent payroll in MXN with bonuses and OT incentives. Agents have a limited self-service portal to see their schedules, request time off, and claim open overtime.

## 4. User Roles & Permissions

Everyone has exactly one `User` (Django auth) + one `Agent` profile row. The profile is the single source of role truth. There is no Django groups/permissions usage — access is by role fields + two boolean flags + middleware.

**`role`**: `agent` or `admin`.
**`role_type`** (12): agents — `training`, `incubation`, `regular_agent`, `kill_team`, `night_shift`; admins — `supervisor`, `qa`, `cs`, `tester`, `sms_email`, `coordinator`, `trainer`.

| Group | Who | Sees / can do |
|---|---|---|
| **Portal users** | `role='agent'` (any type), plus admins with role_type in `{cs, tester, sms_email}` (`PORTAL_ADMIN_TYPES`) | Agent portal only (middleware-enforced). Submit requests, claim open OT, request cancellations, view own data. Inactive portal users see only the "inactive" page |
| **Staff** | All other admins: supervisor, coordinator, qa, trainer | Full staff navigation. Can approve/reject **agent** requests, edit schedules, adherence, codings, uploads. QA/trainer accounts are created with an **unusable password** (they exist as records but cannot log in — only supervisor, coordinator, cs, tester, sms_email admins get working logins) |
| **OT approvers** | role_type `supervisor` or `coordinator`, plus super admins and Django superusers | Additionally: post/edit/delete open OT shifts, approve/reject claim requests and cancellation requests |
| **Staff-request approver** | The one person set as `supervisor` on the requester's profile | The only person who can action a *staff member's own* request (see §6.14). Self-approval blocked for everyone, everywhere |
| **Super admin** | `Agent.is_super_admin=True` (or Django `is_superuser`) | Everything above + the entire Finance section. "Can grant super admin to others" |
| **Official Admin** | `Agent.is_official_admin=True` | Not a permission — a payroll classification. Excluded from the regular Adherence tab; tracked on Finance → Admin Adherence with admin codings; receives the fixed **admin bonus** instead of the adherence bonus |

Other per-agent fields that alter behavior: `track_attendance` (gates dashboard attendance + records), `employer` (LCC / Infinity, default Infinity), `billing_status` (Billed / Not Billed — informational grouping), `status` (active/inactive), `can_auto_code_requests` (super-admin-granted; approving this agent's coding request creates the coding automatically — see §6.14).

## 6. Core Business Logic

### 6.1 Attendance status codes (`AdherenceRecord.status`)

| Code | Meaning | Bonus effect |
|---|---|---|
| `P` | Present | qualifying |
| `T` | Tardy | **disqualifying** |
| `Absent` | Absent (shown as "A") | **disqualifying** |
| `NCNS` | No Call No Show | **disqualifying** |
| `S` | Suspension | **disqualifying** |
| `VTO` | Voluntary Time Off | qualifying; zeroes scheduled hours |
| `IMSS` | Medical/IMSS leave | neutral |
| `MUT` | Make Up Time | qualifying |
| `OT` | Overtime day | qualifying |
| `P+VTO` | Present, then took VTO | qualifying; scheduled capped at hours actually worked |
| `T+VTO` | Tardy, then VTO | **disqualifying** |
| `I` | Incomplete shift | **disqualifying** |
| `T+I` | Tardy and incomplete | **disqualifying** |
| `Quit` | Quit (auto-set by separations) | neutral |
| `Baja` | Terminated | neutral |
| `V` | Vacation | qualifying; zeroes scheduled hours |
| `LOA` | Leave of Absence | **disqualifying**; zeroes scheduled hours |
| `Holiday` | Company holiday, scheduled but **not worked** | qualifying; zeroes scheduled hours |
| `Issues` | Log-in/out issues — Admin Adherence only (`ADMIN_ONLY_STATUSES`), drives the admin-bonus penalty | **disqualifying** |

Statuses are set **manually** by supervisors (cell click or bulk save) or automatically by request approvals (V/VTO/LOA) and separations (Quit/NCNS). Nothing sets `Holiday` automatically — a `nomina.Holiday` row only tags the date header (SYSTEM-SUMMARY.md §13.2). There is **no automated tardy detection** — uploads only zero the hours of scheduled agents missing from the file; they never set a status. That blank, zero-hour row (`_zero_missing_scheduled`) is the upload's record of an **absence**, not of work; anything reading `AdherenceRecord` as evidence an agent is still active has to say so explicitly, or it will read the signal backwards — see §7 item 76.

### 6.2 Adherence bonus

- Constants: `BONUS_QUALIFYING = {P, OT, MUT, VTO, P+VTO, V, Holiday}`, `BONUS_DISQUALIFYING = {Absent, NCNS, T, T+VTO, T+I, I, LOA, S, Issues}` (`wfm/constants.py`).
- **Eligibility**: any disqualifying status in the week → no bonus. An OT shift marked **No Show** also disqualifies. Requires at least one recorded status. Official Admins never get it (they get the admin bonus).
- **Amount** (proportional rule): `bonus = min(max_bonus, final_hours / full_hours × max_bonus)` — defaults **400 MXN max**, **40 h threshold**. At or above 40 final hours → full 400; below → pro-rated (e.g. 30 h → 300 MXN).
- `final_hours` is the week's login+coded hours after all NR deductions.

### 6.3 Admin bonus

Official Admins (`is_official_admin=True`) receive a **fixed** bonus instead: the per-agent `admin_bonus_mxn` if set, else the global `default_admin_bonus_mxn` (**500 MXN** default). Their adherence bonus is forced to zero.

### 6.4 Daily 12.5% not-ready deduction (adherence)

Applied per **day** when a Daily Hours CSV is uploaded (and re-applied whenever codings change):

```
total      = login_seconds + coded_seconds (non-admin codings)
allowance  = total × nr_ratio          (default 0.125 = 12.5%)
excess_NR  = max(0, not_ready_seconds − allowance)
final      = max(0, login_seconds − excess_NR)  →  AdherenceRecord.actual_hours
```

So each agent gets an NR allowance of 12.5% of their worked time; only NR **beyond** the allowance is deducted. Coded time enlarges the allowance but is never itself reduced. This daily math affects the adherence displays and `actual_hours` only.

### 6.5 Weekly NR caps (billing/payroll)

Computed in Finance per agent per week, **from raw login seconds** (not the daily-adjusted values):

- **One weekly allowance**: `nr_allowed = min(cap, connected × 12.5%)`, where `connected` is the pre-deduction total (login + coded). Cap = **6 h** regular, **7 h** for `kill_team` role type.
- **VTO raises it to the flat cap**: any `VTO`/`P+VTO`/`T+VTO` day that week makes the allowance the flat cap instead of the ratio.
- **Deduction** = `max(0, weekly_NR − nr_allowed)`. There is **no 48-hour threshold and no larger-of-two comparison** — `nr_ratio_max_hours` was removed from `BillingSettings` and `BillingSettingsHistory` in migration `0008` (2026-08-05), and the ratio is taken against connected time, not raw login.
- `final_hours = max(0, login + coded − deduction)` → drives both billing and payroll.

Note the adherence tab shows only the flat-cap excess (`max(0, weekly_NR − cap)`) in its `NR Cap Adj` column (its daily 12.5% was already applied at upload); Finance recomputes the full allowance independently from raw seconds.

### 6.6 Cost of Schedule (COS)

Adherence-tab footer measuring % of scheduled hours lost. Per day per agent: `Absent/NCNS/IMSS/S` lose the full scheduled hours; `T`/`T+I` lose `scheduled − actual` (or a default **0.25 h / 15 min** if no login); `OT`/`MUT` hours *above* schedule offset losses **within the same day only**. Day COS % = net loss ÷ scheduled × 100; week = summed. Color bands: 0% green → >35% red.

### 6.7 Billing (Infinity → LCC)

- **Infinity bills LCC** in USD for every agent with at least one **billable Five9 profile** — this applies to `billing_report`/`billing_export` (v1); `billing_export_v2` uses a different roster (see below).
- `billing_usd = final_hours × rate`, where rate = per-agent `billing_rate_usd` override or the global `billing_rate_usd` (**$15.00/h** default).
- **Multi-account agents**: only `DailyAgentHours` rows whose Five9 username belongs to one of the agent's *billable* profiles count; non-billable accounts (e.g. a Kill Team OT login) are excluded. The primary billable username is used for display.
- OT base hours are already inside `final_hours` (agents log into Five9 during OT), so billing needs no separate OT line; incentive top-ups and bonuses are shown as separate USD-equivalent totals.
- Report groups by employer (Infinity vs LCC Direct) then by role type; separated agents drop off from their `remove_from_adherence_date` week.
- **`billing_export_v2`'s roster is not billable-Five9-gated.** It uses the same active-or-still-in-pay-window rule as other Finance exports, plus excluding `employer='LCC'` — no billable-Five9-profile filter. An agent with no billable Five9 hours that week still gets a row, zero-filled, rather than being dropped. It also carries its own **Shift Hours** column (position D, ahead of the login/NR/deduction chain) — same definition and same underlying calculation (`adherence.views._compute_shift_hours`) as the combined Adherence export's Shift Hours column, so the two reports cannot disagree on this number. It is schedule data, not a billing input — it plays no part in `billing_usd`.

### 6.8 Payroll (MXN)

- Base pay = `final_hours × hourly_rate` (per-agent MXN rate, default **62.50 MXN/h**).
- **OT incentive top-ups** (only `status='completed'` OT shifts count; these are premiums *on top of* base pay since the base OT hour is already in `final_hours`):
  - Time & a Half → extra `0.5 × rate × incentivized_hours`
  - Power Hour → extra `1.0 × rate × incentivized_hours` (2× total)
  - The docstrings identify these premiums as LCC-funded incentives.
- Total pay = base + top-ups + adherence bonus **or** admin bonus. USD equivalent via the `usd_to_mxn` setting (default 17.0).
- **Commission deduction %** is stored per agent-week (`PayrollAdjustment`) and *displayed* on payroll — **but it is never actually subtracted from total pay** (see Quirks), and the "Comm. Earned" export column is hardcoded to "—" ("commission earnings tracking coming soon").
- Reports split Infinity vs LCC Direct employees; the totals block covers Infinity only.

### 6.9 Per-week versioned financial settings

`BillingSettings` is a singleton holding every rate: billing rate, USD→MXN, NR caps (6/7), NR ratio (0.125), 48-h ceiling, tardy default (0.25), bonus max/threshold (400/40), default admin bonus (500). Saving from Finance → Settings picks an **effective week**; the values are snapshotted into `BillingSettingsHistory` keyed by that week's Monday *and* written to the singleton. All calculations call `get_for_week(week_start)` — the most recent snapshot at or before that week — so **historical weeks always recompute with the rates that were in force then**.

### 6.10 Five9 CSV uploads

Two distinct formats:

1. **Daily Hours** (Adherence → Daily Hours, one per day): columns `AGENT`, `LOGIN TIME`, `NOT READY TIME` (+ optional `AGENT GROUP`), times as HH:MM:SS. Rows match to agents by **Five9 username** (case-insensitive) via `Five9Profile`; unmatched rows are kept and can be re-matched later. On upload: daily NR math runs (§6.4) for the *billable* row only, and every agent who was scheduled that day but absent from the file gets `actual_hours = 0` (no status set). Re-uploading a date replaces it.
2. **Login-Logout report** (OT Shifts → Verify): columns `AGENT`, `DATE` (YYYY/MM/DD), `LOGIN TIMESTAMP` / `LOGOUT TIMESTAMP`. Builds `AgentLoginSession`s and verifies every OT shift on those dates: Five9 session time and coding time are clipped to the shift window, merged, and stored as `OTShiftVerification` (coverage %, "username not found", "covered by codings" annotations shown on the OT grid).

3. The **Staffing Calculator** has its own third upload: the Five9 *ACD Queue Quality of Service Details – Hourly* report (call volumes per day/hour).

### 6.11 Staffing Calculator (Erlang C)

- Upload hourly call volumes per week; parameters per week: target SL (default 80% in 20 s), shrinkage %, AHT (default 420 s), and **weeks of data** — a default plus optional per-day overrides (volumes are divided by weeks to get an hourly average).
- Erlang C computes Agents Required, then +shrinkage.
- **Scheduled Staff** counts, per (day, hour): call-role agents (`regular_agent`, `night_shift` — role checked **as of the viewed week** using RoleHistory for past weeks and pending role changes for future dates) from Shift overrides falling back to effective ShiftTemplates, **plus every non-cancelled OT shift for any agent regardless of role**. Overnight shifts split at midnight; each agent counts once per hour. Click a number to see who.
- **OT visibility columns**: "OT Posted" = open/filled posting counts overlapping the hour; "Net Gap" = `max(0, required − scheduled) − open_postings` (filled postings already count inside Scheduled Staff, so they are *not* subtracted again). Red = post more, amber 0 = covered only by unclaimed postings, green ✓ = covered. "+ Post OT" pre-fills the posting modal with date/hour/gap-count and returns to the calculator.
- Open (unfilled) postings **never** count as coverage — they aren't `OvertimeShift` rows at all.
- **Two exclusion rules narrow Scheduled Staff, and they are deliberately separate — full detail in §7 items 74–76.** (a) A `STAFFING_EXCLUDED_STATUSES` status (`V`, `VTO`, `LOA`, `Holiday`, `IMSS`, `S`) drops the agent **on that day only** (`8ab51b3`); partial-work and no-show statuses (`P+VTO`, `T+VTO`, `Absent`, `NCNS`, `T`) still count, since those agents provided real coverage or were an unplanned no-show rather than a pre-planned absence. (b) A `SEPARATION_MARK_STATUSES` status (`Quit`, `Baja`) drops them on that day **and every day after it** (`4092f1b`), so a mark keeps excluding the agent through later weeks holding no adherence data at all — gated by a rehire guard (an open `EmploymentPeriod` starting on or before the mark date) and a 180-day look-back, with every ambiguous or missing-data case falling through to counting the agent. Both halves of this forward-sticky rule shipped broken and were fixed in `6fc3ed9` + `5d8c2e4` (§7 item 76). The popover shows a muted status tag beside each counted agent's name when a record exists for that date, a header summary line counting non-Present statuses among those still counted (e.g. "19 scheduled · 4 Absent, 2 T"), and moves any excluded agent to a quiet "Also scheduled" line naming their reason, rather than vanishing them. **OT is never excluded by either rule** — a quit-marked or on-leave agent's approved OT still counts as coverage. These sets are Staffing Calculator only; neither affects bonus, Cost of Schedule, payroll or hours.

### 6.12 Scheduled role changes & RoleHistory

- A supervisor schedules a future role change (new role type, optional new supervisor and new weekly schedule) from the agent detail page; **one pending change per agent**.
- The new schedule is written into ShiftTemplates **immediately** (effective-dated), so Shifts/Adherence/Staffing show the future schedule before it applies; cancelling the change reverses those templates.
- The change **applies** automatically on/after its effective date via three redundant paths: a middleware that runs once per calendar day on the first request, lazily whenever that agent's detail page loads, and a management command for cron.
- Application updates the Agent's role/role_type/supervisor, propagates role_type to matching Five9 profiles, closes the open `RoleHistory` row and opens a new one. `RoleHistory` (with `effective_from`/`effective_to`) is also written on any manual role-affecting edit and is what keeps the Staffing Calculator historically accurate.

### 6.13 Separation process

- Processed from the agent detail page; two modes:
  - **In Progress**: nothing changes — the agent stays active while termination documentation is collected (the detail page shows days-since-last-day and 30-day NCNS/Absent counts). Can later be finalized or cancelled.
  - **Finalized** (requires `remove_from_adherence_date`, expected to be a Monday by convention only — the UI shows help text and Monday-snap shortcut buttons, but the date field is freely editable and nothing server-side rejects a non-Monday value): sets the agent inactive, stops attendance tracking, stamps the termination date, closes the open EmploymentPeriod with a mapped reason, **cancels all future pending OT shifts**, **auto-rejects pending requests**, **cancels future pending role changes**, and auto-codes the remainder of the last week (days after the last day worked): quit/terminated → `Quit`, abandonment → `NCNS`; contract-end and resigned-notice are not auto-coded.
- The agent remains on Adherence/billing until their `remove_from_adherence_date` week. Recently-separated agents still show on the adherence grid until that date passes.
- Cancelling an in-progress separation keeps the agent active. **There is no un-finalize flow** — reversing a finalized separation is manual.

### 6.14 Request system

**Types** (one `AgentRequest` model): Coding, Vacation, Day Off Change (one-time or permanent), VTO, LOA, Schedule Change.

Coding-request times are entered as **typed 24-hour `HH:MM:SS`** text (seconds optional — `14:30` saves as `14:30:00`), matching the Codings tab rather than a native time picker, and are validated server-side in the coding branch of `_fill_request_from_post` with the Codings tab's zero-pad-hour + `time.fromisoformat` + end-after-start check (`44c027e`). The end-after-start comparison is also what enforces "cannot cross midnight" for a request. Request detail shows these times as `H:i:s` so an approver sees the exact stored value; `AgentRequest.summary()` and the Team Requests list stay on `H:i`.

**Who approves what:**
- **Agent requests** — any staff user can approve/reject/mark-done.
- **Staff requests** (supervisors/coordinators/admins submitting for themselves via Requests → My Requests): actionable **only** by the supervisor on the requester's profile (snapshotted at submission as `assigned_supervisor`). Others see the request read-only with "Only [name] can action this request." Submission is blocked if no supervisor is assigned.
- **No one can ever action their own request**, including the self-supervisor edge case.

**Auto-apply on approval** (identical for agents and staff):
- Vacation → `V` on each day; VTO → `VTO` on the date; LOA → `LOA` on scheduled working days only. (V/VTO/LOA zero or adjust scheduled hours per §6.1.)
- Day Off Change: one-time → `Shift` overrides (new day off + old day working); permanent → effective-dated `ShiftTemplate` updates.
- Schedule Change → `_save_shift_template` per selected weekday from the effective date.
- Coding → **no auto-apply by default** (status-only): requesters only estimate their missed time, so the supervisor pulls the exact amount and enters the coding manually on the Codings tab. **Exception (`d4fd7d6`)**: if the requesting agent has `can_auto_code_requests=True` — checked at **approval** time, on the requesting agent, not at submission — approval creates the `Coding` itself via the shared `adherence.views.create_coding` and marks the request **done** in the same action (`done_by` = the approver). `is_admin_coding` mirrors the agent's `is_official_admin`, so an Official Admin's row lands in Admin Codings and a regular agent's in Codings. Provenance is written to the coding's `notes` (source request number + approver) and the request's `auto_action_log` (which records that the system completed it rather than a supervisor confirming it). See §7 items 52–53 for the recompute rule and the deliberate absence of date/separation checks.
- Everything is logged (`auto_action_log` on the request + Activity Log); unread badges flow both directions (approver on submit, requester on response).

**Open OT shifts**: OT approvers post unassigned shift slots (multi-count for identical slots). Everyone can request them (agents via Available OT, staff via the OT grid). Multiple pending requests per shift are allowed as backups; approving one **creates a real `OvertimeShift`** for the winner (base rate = their hourly rate; incentivized hours = full shift length if an incentive is set), fills the posting, and auto-rejects the backups. Rejection returns the shift to fully open. Deleting a posting soft-deletes it (`removed`) and rejects pending claims with a notice.

**One request per slot, per agent** (`b544e4d`): a claim is refused when that agent already has a pending claim for the same date and times on **any** posting, or a non-cancelled `OvertimeShift` at those times. Multi-count postings are why the check is keyed on the slot rather than the posting — the older per-posting check let an agent request identical postings one after another. Exact time match only, so split OT at different hours on the same day is unaffected. Overlap with a regular scheduled shift is a **separate** check, added later in `7b7e0b5` and keyed on intervals rather than exact times (§7 item 69). A **rejected** claim leaves the slot re-requestable with no special case, since the guards see only pending claims and live OT rows. Guards and create share one `transaction.atomic()` with `select_for_update()` on the posting, closing a double-click race that no DB constraint would have caught (§7 item 57).

**OT cancellation requests**: a shift's owner submits a reason; the shift **stays assigned and fully counted** until an approver acts. Approval flips it to the existing `cancelled` status (drops out of hours, pay, staffing); rejection changes nothing — a missed shift is then a normal No Show.

## 7. Known Quirks & Implementation Details

1. **Commission deduction is display-only.** `PayrollAdjustment.commission_deduction` is entered and shown on payroll, but never subtracted from `total_pay_mxn`; the "Comm. Earned" export column is hardcoded `'—'` ("coming soon").
2. **Two separate NR mechanisms.** The daily 12.5% deduction (adherence, writes `actual_hours`) and the weekly cap/48-h check (finance, recomputed from **raw** `login_seconds`) are independent — Finance does *not* reuse the daily-adjusted values. Don't "fix" one by making it read the other without understanding both.
3. **`recalculate_actual_hours` management command drifts from the live code**: it hardcodes `0.125` instead of reading `nr_ratio` from settings, and it does not exclude admin codings when summing coded time (the live `_refresh_actual_hours` does both correctly).
4. **Scheduled Staff includes assigned OT.** In the Staffing Calculator, every non-cancelled `OvertimeShift` counts as coverage regardless of role. This is why Net Gap subtracts only *open* postings — subtracting filled ones would double-count.
5. **Access control is middleware-only for most staff views.** Beyond `AgentAccessMiddleware` keeping portal users out, destructive staff views (agent delete, shift edits, role changes) have no supervisor-vs-other-staff distinction. The exceptions with real per-view gates: Finance (`finance_access_required`), OT posting/approvals (`_is_ot_approver`), staff-request actioning (assigned supervisor), and separations (manual role check).
6. **Login rules**: only supervisor, coordinator, cs, tester, sms_email admins and `role='agent'` users get working passwords; QA/trainer accounts are created with unusable passwords. `teams_password` and `Five9Profile.five9_password` are plain stored credentials (viewable in the UI), unrelated to Django auth.
7. **Session policy**: 4 h inactivity timeout, 16 h absolute, expire on browser close; AJAX gets `{'expired': true}` 401s, pages redirect to login with a banner.
8. **`Agent.five9_username`/`five9_password` are dead legacy fields** — superseded by `Five9Profile` (multi-account with `billable` and `is_primary` flags); only a data migration ever read them.
9. **"Best template" resolution is duplicated** in six places with identical rules (overrides beat templates; among templates covering the date, latest `effective_from` wins, NULL = forever): the canonical `scheduling.views._best_shift_template` (reused three times — `agent_my_shifts`, `erlang.views`, and, since Phase D (`3f57b39`, item 70), the shared `_resolve_schedule_blocks` that both `_ot_schedule_conflict` (item 69) and `_resolve_agent_week_schedule` (item 70) call rather than resolving templates a fourth way), plus five independent reimplementations — `shift_list`, `shift_week` (both `scheduling/views.py`), and `adherence.views._build_maps`, `adherence.views._effective_template` (promoted from a closure nested in `_build_rows` to a module-level function, see item 18), and `agent_my_adherence` (all three `adherence/views.py`). A known consolidation candidate, not consolidated as part of this work — change one, check all six.
10. **`_save_shift_template` deletes future templates** (`effective_from > effective_date`) when writing a permanent change — a schedule change wipes any already-scheduled later changes for that day.
11. **Silent exception swallowing** in `ApplyScheduledRoleChangesMiddleware` and `AgentAccessMiddleware` — failures to apply role changes or compute badges are invisible.
12. **Role changes apply on first request of the day** (cache-keyed), not on a guaranteed cron. The management command exists but is a backstop, not scheduled by the repo.
13. **Coding blocks cannot cross midnight** — overnight coded time must be split into two entries (enforced in the UI).
14. **Cell/status colors, badge patterns, and modals are consistent conventions**: Pending gray, Approved green, Rejected red, Done blue; red `nav-badge` bubbles; inline-styled modals. Match them for anything new (standing owner instruction: simple, clean, consistent, minimal clicks, no full-page reloads for small updates).
15. **`db.sqlite3` is gitignored and untracked — it is NOT committed.** `.gitignore` line 1 covers it (plus `-shm`/`-wal`); it was tracked historically and deliberately removed in `ed1022e` ("Add .gitignore; stop tracking db.sqlite3"). Consequence: local database state does not travel with the repo. Every developer has their own file, so **a local DB can be missing migrations that are already applied in production**, or hold rows nobody else has — verify with `python3 manage.py showmigrations` instead of assuming a fresh checkout is migrated. Production data lives in Render Postgres. A stale `test_path.py` (21 KB) sits at repo root.
16. **Hardcoded supervisor sort priority** in the Shifts grid admin section: `{'Jesus Urbina': 0, 'Andrea Jones': 1}`.
17. Timezone: `TIME_ZONE = 'America/New_York'` (`USE_TZ = True`) in `wfm/settings.py` — not Mexico City. Practical consequence: for a user working from US Pacific time, actions taken after roughly 9 PM Pacific are recorded on the *following* server date, and any week-scoped view opened without an explicit `?week_start=` defaults to the server's current week, which can already be Monday of the next week from that user's perspective. Weeks always run Monday–Sunday, and "week_start" params are snapped to Monday.
18. **Shift Hours has exactly one implementation.** `adherence.views._compute_shift_hours` (module-level, added in `577774e`) is the single source of the "raw regular-schedule hours" summation; `_build_rows` delegates to it instead of accumulating inline, and `finance.views.billing_export_v2` calls it directly (via `_build_maps`, never `_build_rows`) for its own Shift Hours column. Overtime — including OT spillover from the previous day — still determines whether a day counts as scheduled at all (`is_scheduled_day`); it just never contributes to the summed hours. That distinction is subtle and easy to break if this function is ever "simplified."
19. **Production Postgres can carry orphaned columns from reverted features.** Deleting a migration file does not undo it on a database it already ran against — Django's migration loader builds its graph only from files on disk, so an already-applied migration whose file is gone simply leaves its schema change in place with no code anywhere admitting it exists. This is invisible locally (SQLite never had the migration applied, so it can't reproduce) and invisible to `makemigrations --check` (the models and the migration files on disk genuinely agree; the mismatch is between the code and the *production* database). When a write fails only in production, read the Render Postgres log before theorizing — that log was the only artifact that could identify item 20 below.
20. **`can_access_admin_attendance` still exists on production's `scheduling_agent` table**, `NOT NULL`, now with a database-level default of `false` (migration `0048_set_default_admin_attendance_column`). It has no model field — it's a deliberately preserved orphan from the fully-reverted Admin Attendance feature (item 9 above; `c1772c0` → `4f88bb9`/`f7045d2`). If Admin Attendance is ever re-landed, a fresh `AddField` under a new migration number will try to add a column that already exists on production and will fail the deploy — it must be handled as an existing-column case, not a plain `AddField`.
21. **Production's `django_migrations` table very likely still records `('scheduling', '0046_agent_can_access_admin_attendance')`**, even though that file was deleted in the revert (its migration number was later reused by the unrelated, currently-real `0046_agent_can_access_admin_tabs`). This is understood and inert, not something to fix: Django's migration loader matches applied rows against files on disk by exact name, and an orphaned row with no matching file is never visited or loaded into the graph.
22. **An agent profile can be missing while its Django `User` row exists.** Such a person is structurally invisible in the Users tab and the Adherence tab (both are built from agent profiles), while their username is still taken — the symptom is a "user already exists" error for someone nobody can find in either tab. Django admin at `/admin/` is currently returning 500s on production, so it is not a usable diagnostic route for tracking these down.
23. **A fifth app, `nomina/` (payroll), exists in the repo and is not described anywhere in this document or in SYSTEM-SUMMARY.md.** It has its own `_infinity_agents`, `_admin_agents`, and `_pay_window` predicates in `nomina/views.py` — separate from the pay-window predicate described elsewhere in this document (item on duplicated predicates, §6.7/§6.8) — and has not yet been audited for consistency with it. This is a known documentation gap, not an oversight to "fix" opportunistically: any future work touching payroll must read the live `nomina/` code rather than trusting these docs.
24. **`Agent.adherence_start_date`** (nullable date, migration `0049_agent_adherence_start_date`) controls the first week an agent can appear on the Adherence tab. `NULL` means the previous behavior exactly — it is a **floor only**: it can remove an agent from a week, never add one, and appearing on a week still requires passing the existing activity gate (item 25 below). Must be a Monday, validated server-side in `AgentForm.clean_adherence_start_date` on both `agent_create` and `agent_edit`. The filter lives in the single shared helper `_get_adherence_agent_pks`, so `finance.views.adherence_export` stays consistent with the Adherence screen automatically.
25. **The Adherence activity gate is not date-scoped.** `_get_adherence_agent_pks` includes `Q(shift_templates__isnull=False)` as part of what makes an agent "active enough" to show on a given week — any shift template satisfies this for every week, including weeks before the agent's `adherence_start_date` (item 24). `adherence_start_date` is not referenced anywhere in the roster or row-building logic beyond that one filter. This is known and deliberately unchanged.
26. **[FIXED as of `23c67a8`]** `_get_adherence_agent_pks` used to cache its result for 300 seconds per `(week_start, supervisor_id)`, so changes to `adherence_start_date`, `status`, or `track_attendance` could take up to 5 minutes to appear on the Adherence tab, and any test that queried the same week twice had to call `cache.clear()` between calls or it would read a stale roster and pass for the wrong reason (those `cache.clear()` calls are still in the test files — now harmless no-ops, left alone rather than cleaned up as out of scope). The cache stopped paying for itself once `86ab564` (item 54) cut the query's cost to single-digit milliseconds, so it was removed outright rather than shortened. The helper is now deliberately uncached — see item 61.
27. **There is no indicator anywhere that an agent has been floored out of a week by `adherence_start_date`.** An accidental value silently removes them from the tab, which stops them being coded and stops adherence bonus qualification, with no visible warning.
28. **Five9 hours are matched to an Agent at upload time and stored as a nullable FK on `DailyAgentHours`** (see §5). Rows uploaded before an agent existed keep `agent_id` `NULL` permanently — no signal, cron, or save hook ever re-scans them. Billing and payroll query by that FK, so unmatched rows contribute nothing. Consequence: an agent created after their hours were uploaded shows zero actual hours until someone manually clicks Rematch on each affected day in Daily Hours. There is no global unmatched view — the only surfacing is a per-day badge. Such an agent may still appear as a **row** on Billing v2 and Nómina, because those rosters do not require matched hours — appearing is not evidence that hours are attached.
29. **`is_admin_coding` is stamped on a `Coding` at creation time by which endpoint was used, and never changes.** Because both the Codings and Admin Codings tabs filter on the agent's *live* `is_official_admin` roster **and** on `is_admin_coding`, flipping `is_official_admin` can leave an agent's existing codings invisible on both tabs without deleting them, while `_refresh_actual_hours` continues counting them into `actual_hours`. This is an existing failure mode, not hypothetical. `AdherenceRecord` rows have no admin flag and simply re-route on the next page load.
30. **The admin-bonus formula** (`agent.admin_bonus_mxn` or `settings.default_admin_bonus_mxn`) is hand-copied in three places in `finance/views.py` (`_get_billable_weekly_data`, `admin_adherence`, `admin_adherence_export`). The `is_official_admin=True` admin roster filter is independently re-run in five places. Any change to admin bonus logic must touch all three copies.
31. **[FIXED as of `2ecb0c7`]** A Recurring save in the Shifts editor used to appear to do nothing in the selected week. A specific-date `Shift` override always wins over a `ShiftTemplate` (§3), and the Recurring branch of `shift_week` wrote the new template correctly but never touched any `Shift` rows already sitting in that week — left behind by a prior One-time save, Copy-prev-week, or the Adherence quick-edit modal (see items 46–47). The grid kept rendering the stale override, so the change looked like it silently took effect only the following week, once the override-free week arrived. A Recurring save now also deletes the agent's `Shift` overrides inside the week on screen, from the chosen effective date forward — never touching another week. The Shifts save path had zero automated test coverage before this fix; see `ShiftSaveTests` in `scheduling/tests.py` (381 → 401 tests).
32. **`_finalize_separation` permanently sets `track_attendance=False`.** `records_attendance` and `records_hours` (`scheduling/views.py`) both filter on `agent__track_attendance=True`, so once a separation is finalized, that agent's entire historical attendance and hours disappear from Records — including weeks they actually worked, not just future ones.
33. **[FIXED as of `4f23ec5`]** `payroll_report` and `payroll_export` (`finance/views.py`) used to base their roster on `Q(track_attendance=True) | Q(five9_profiles__billable=True)` alone. A separated agent with no billable Five9 profile failed this filter outright, regardless of the pay-window `.exclude()` layered on top — they dropped out of their own final pay week despite satisfying the pay window. A third OR branch, `Q(status='inactive', separations__status='finalized', separations__remove_from_adherence_date__gt=week_start)`, now covers this case in both views.
34. **Several week-scoped views filter on `status='active'` with no pay-window predicate at all**, so finalizing a separation removes the agent from every past week at once: `finance_dashboard`, `admin_codings`, `admin_adherence`, `admin_adherence_export`, the Official Admin half of `adherence_export`, and `adherence.views.payroll_export`.
35. **`scheduling.views.agent_list`'s export branch applies the pay window against today's Monday** (`today - timedelta(days=today.weekday())`), not the week actually being viewed, and the on-screen table applies no pay-window predicate at all — a finalized separation removes the agent from the Users list immediately, regardless of which week is selected on screen.
36. **Reactivations and other agent status changes are not written to the Activity Log.** `agent_edit`'s change-detail logging tracks username, legal name, email, display name, role, role type, employer, and billing status — `status` is not among them, so flipping an agent active/inactive leaves no Activity Log trail. Separately, the Records → Separations page's "Processed On" column shows a date only, with no timestamp.
37. **[FIXED as of `d167897`]** `remove_from_adherence_date` was not server-validated as a Monday on the separation form — `process_separation` only parsed it as a valid date, and the field was a free `<input type="date">` with only client-side "Next Monday"/+2/+3-week shortcut buttons, so a typed non-Monday value reached the database silently. Both `process_separation` and `update_separation` now reject a non-Monday value server-side (view-layer only, never on the model), and the field is a server-rendered dropdown of labeled Mondays so a bad value can't be typed in the first place — see also §6.13.
38. **[FIXED as of `23c67a8`]** The roster cache in `_get_adherence_agent_pks` used to be invalidated only by its 300-second TTL, never on writes, and `LocMemCache` (no `CACHES` backend is configured in `wfm/settings.py`) meant that TTL wasn't even consistent across gunicorn workers. See item 26.
39. **The pay-window `.exclude()` in `payroll_report` and `payroll_export` (`finance/views.py`) fires if ANY of an agent's separations has `remove_from_adherence_date <= week_start`**, not just the separation governing their current employment — all three conditions in the exclude (`status='inactive'`, `separations__status='finalized'`, `separations__remove_from_adherence_date__lte=week_start`) are evaluated against a single joined separation row, but an agent can have more than one. An agent rehired after a prior finalized separation, then separated again, has two separation rows; the old one's past `remove_from_adherence_date` wrongly excludes them from their *current* final pay week even though the current separation's date is still in the future. Pre-existing, not introduced by `4f23ec5` — blocking for any future rehire-then-separate scenario.
40. **`adherence.views.payroll_export` computes its own hours from `AdherenceRecord.actual_hours`** instead of calling `finance._get_billable_weekly_data`, the shared engine that recomputes final hours from raw `DailyAgentHours` seconds every time. This violates the core rule that billing and payroll must never read `actual_hours` — its "Actual Login Hours"/"Adjusted Total Hours" columns can disagree with what `finance.payroll_report`/`payroll_export` show for the same agent-week. Pre-existing and unfixed.
41. **The `remove_from_adherence_date` Monday check (item 37) is view-layer only, in `process_separation` and `update_separation` — deliberately, not an oversight.** Legacy non-Monday values written before `d167897` still exist in production and still load and save normally, since nothing on `AgentSeparation` itself enforces this. Any new write path for this field added in the future must add its own Monday check; the model will not catch it.
42. **The Remove-from-Adherence date dropdown only offers Mondays four weeks back through eight weeks forward (`wfm.utils.get_monday_choices()`), by design.** A wider past range would make it easy to retroactively hide an agent from months of adherence/billing/payroll history through this field. A separation that genuinely needs a date outside that window cannot currently be set through the UI.
43. **The Shifts week editor's Permanent/One-time radio now defaults off `agent_has_recurring`** (does the agent have a `ShiftTemplate` row at all, on any week) **as of `2ecb0c7`** — previously it used `has_any_template`, which only asks whether a template covers the week currently on screen. `has_any_template` still means exactly that and is unchanged everywhere else it's used (the blue "Recurring schedule active" banner, the day-field prefill). The old logic meant opening a past week for an agent whose recurring schedule started later could silently pre-check Permanent — and since `_save_shift_template` deletes every future template for a day-of-week on a Permanent save (item 10), an unnoticed click there could wipe the agent's entire forward schedule history. Separately, `shift_week` used to default a missing or unrecognized `edit_type` POST value straight to `'permanent'`; it now rejects the request server-side with nothing written.
44. **The Shifts week editor shows a confirmation dialog before a Permanent save in two independent cases, added `2ecb0c7`**: (1) the chosen effective date falls before the real current week — a retroactive save that rewrites every week from there to now, not just the one on screen — and (2) the save would remove an approved day-off request (items 45–46). Either can fire alone; when both apply they render together in one dialog. The data for both is rendered server-side into the page (`day_off_warnings` in the `shift_week` context, embedded via Django's `json_script` filter) and read by the page's own JavaScript at submit time — there is no separate AJAX call.
45. **A Permanent save on the Shifts editor can silently delete an already-approved future recurring day off — pre-existing behavior, not introduced or changed by `2ecb0c7`, only warned about.** `_save_shift_template` (item 10) deletes every `ShiftTemplate` for a day-of-week whose `effective_from` is after the new effective date, and `shift_week`'s form resubmits all seven days on every save — so this fires for every day-of-week the agent has a template for, regardless of which days a supervisor thinks they're editing. Approving a `day_off_change` request with `day_off_type='permanent'` writes exactly this kind of template. When it gets wiped, the `AgentRequest` record itself is untouched: `status` stays `'approved'` forever and `auto_action_log` keeps its original approval text, which becomes a false historical claim the moment the schedule is overwritten. The Shifts tab now warns before this happens (item 44); nothing else does.
46. **`Shift` override rows carry no origin field.** An override created by approving a one-time `day_off_change` request is stored identically to one created by Copy-prev-week, the Adherence quick-edit modal, or any other One-time/Specific-Date save — same `agent`/`date`/`start_time`/`end_time`/`is_off`/`notes` fields, nothing recording where it came from. This is why the fix in item 44 warns before deleting rather than silently skipping approved-request overrides: there is no reliable way to tell them apart from ordinary stale ones without a schema change.
47. **Four places create `Shift` overrides**, all indistinguishable per item 46: the Adherence tab's quick-edit modal (its "Apply to agent profile permanently" checkbox defaults **unchecked**, making this the most common source of the stale overrides that item 31 used to leave stranded), "Copy prev week" / "Copy prev week (overwrite)" on the Shifts grid, any One-time or Specific-Date save in the Shifts editor, and approving a `day_off_change` request with `day_off_type='one_time'`.
48. **The Shifts week editor's day-field prefill resolves the schedule at the week's Monday only** (`shift_week`'s GET path), while the grid (`shift_list`) and the Adherence engine resolve per day. After a mid-week Recurring save with effective date = Today, the grid correctly shows the new schedule from today forward while the editor for that same week still prefills the old times for the whole week. Re-saving from that stale form propagates the old times back out. Not fixed as part of `2ecb0c7` — noticed during that work, left out of scope.
49. **`nomina/views.py` reads the resolved shift schedule for money in three places**: vacation pay (`_vacation_hours` — each `V` day pays `min(scheduled_hours, 8)`), holiday hours, and admin-bonus proration (`_admin_bonus_factors` — prorates the Official Admin bonus by worked-days ÷ scheduled-days). None of these move unless the affected week contains a `V` (or Holiday) status — with no such day, `_admin_bonus_factors`'s prorate is always exactly 1.0 regardless of the schedule shape (pinned by a test). When a `V` day does exist, measured: roughly 100 MXN of admin bonus moves per vacation day that shifts onto or off a scheduled day, capped at the full bonus, plus a further vacation-pay change if the shift's length also changes on that day. Official Admins only — regular agents never receive the admin bonus.
50. **The adherence bonus does not depend on scheduled hours — verified by direct measurement, not just by reading the code.** `bonus_mxn` (`adherence.views._build_rows`) is computed from `final_adjusted` (actual login hours plus coded hours, minus the NR-cap deduction) and from `AdherenceRecord.status` alone; the money-side formula in `finance.views._get_billable_weekly_data` uses `final_hrs` and `AdherenceRecord.status` the same way. Neither reads the schedule. Confirmed by swinging one agent's scheduled hours from 0 to 56 across four different schedules with zero change to `bonus_mxn`; pinned by `test_adherence_bonus_unaffected_by_schedule_change` in `ShiftSaveTests`.
51. **The two Shifts-editor warning dialogs added in `2ecb0c7` (item 44) are JavaScript, and this project has no JS test runner.** `ShiftSaveTests` verifies the server-rendered data both dialogs read (`day_off_warnings`, `current_week_start_iso`) is assembled correctly, and that both triggers' data can be present at once — it does not execute the dialogs or their confirm/cancel behavior.
52. **`_refresh_actual_hours` must fire for regular codings ONLY — this is the easiest thing to get wrong when creating a `Coding`.** Since `d4fd7d6` there is exactly one creation path, the module-level `adherence.views.create_coding(agent_id, coding_date, start_time, end_time, notes, is_admin_coding)`, with two callers: the Codings tab's `add_coding_ajax` and the coding-request auto-code hook in `scheduling.views._auto_code_approved_request`. It calls `_refresh_actual_hours` **only when `is_admin_coding` is False**. 74. **Staffing Calculator: exclude agents on leave from Scheduled Staff (`8ab51b3`).** Scheduled Staff previously counted an agent's shift/template coverage even when their adherence status that day meant they weren't actually on the floor (vacation, VTO, LOA, etc.), overstating who'd really be available. New `wfm.constants.STAFFING_EXCLUDED_STATUSES = {V, VTO, LOA, Holiday, IMSS, S}` — deliberately separate from `SCHED_HOURS_ZEROING_STATUSES` (pay/hours engine), `BONUS_QUALIFYING`/`BONUS_DISQUALIFYING` (bonus eligibility) and `COS_INCLUDE_STATUSES` (Cost of Schedule); merging any of these would change payroll, bonus, or Cost of Schedule, so this set exists for the Staffing Calculator's Scheduled Staff count alone — is checked in `erlang._build_scheduled_map` against the agent's adherence record for that date, **same-day only**. Partial-work statuses (`P+VTO`, `T+VTO`) and no-show statuses (`Absent`, `NCNS`, `T`) are deliberately NOT excluded: those agents provided real coverage or failed to show up unexpectedly, neither of which is a pre-planned absence. **Overtime is untouched** — any non-cancelled `OvertimeShift` still counts as coverage regardless of the agent's adherence status that day, exactly as before.

A Cost of Schedule regression test was added pinning `IMSS` and Suspension (`S`) as full-loss days; Cost of Schedule itself did not change, the test only pins what was already true so a future change can't accidentally alter it while touching this area.

75. **Staffing Calculator: exclude agents marked Quit or Baja from that date forward (`4092f1b`).** Supervisors mark an agent's adherence cell `Quit` or `Baja` days or weeks before the formal separation is processed. Until it is processed the agent is still `status='active'`, so Scheduled Staff kept counting them as coverage — and adding `Quit`/`Baja` to item 74's `STAFFING_EXCLUDED_STATUSES` would not have fixed this, since that set only drops the specific marked days, so the agent would reappear in the count the following week once no adherence data exists for it.

New `wfm.constants.SEPARATION_MARK_STATUSES = {Quit, Baja}`. Unlike `STAFFING_EXCLUDED_STATUSES`, it applies from the marked date **forward**, not just on the marked day, so the agent stays out of later weeks holding no adherence data at all. A new `erlang._build_quit_mark_map()` resolves each agent's standing mark from three bulk queries (one row per agent each): the latest mark, the latest activity, and the employment floor — no per-agent or per-hour query, and the existing week-scoped adherence query from item 74 is untouched, so the leave-exclusion path and the popover's status tags cannot regress from this change.

Four rules keep this from ever erasing someone who is really working:
  - **Rehire guard.** The rule only fires when the agent has an open `EmploymentPeriod` and the mark falls on or after that period's start. `_finalize_separation` is the one thing that closes a period, so its absence means the agent is separated-and-not-properly-re-onboarded — exactly the rehire state where the agent must keep counting instead of vanishing. A mark predating the current period belongs to a previous stint and is ignored, so an agent who quit months ago and came back is never erased.
  - **Reinstating activity must come from a day that has already happened** (`date <= min(today, week_end)`). Otherwise a single pre-approved future `V`, `LOA` or `Holiday` would out-date the mark and silently switch the exclusion off, since approving a vacation request writes a status onto every calendar day of the approved range. Marks themselves are deliberately NOT capped at today, because `_auto_code_separation_week` legitimately writes future-dated `Quit` days for the rest of the separation week.
  - **180-day look-back** on the mark query. An older mark fails toward counting.
  - **Every ambiguous or missing-data case falls through to counting the agent.** Overcounting is visible; silently erasing a working employee is not.

`excluded_map` now dedups on `(day, hour, agent)` the way the counted map already did, since exclusions become common with this change — an agent reachable via both a template and a pending role change now lists once in the popover rather than twice (`excluded_seen`, confirmed by `git log -S "excluded_seen"` as shipping in this commit, not any other).

**Known accepted limitation:** a `Quit` or `Baja` typed onto a far-future date excludes that agent from then on with no automatic recovery. Visible in the popover, cleared by removing the mark. Deliberate, not an oversight.

No bonus, Cost of Schedule, payroll or overtime behavior changed. `Quit` and `Baja` remain absent from `BONUS_QUALIFYING`, `BONUS_DISQUALIFYING`, `COS_INCLUDE_STATUSES`, `SCHED_HOURS_ZEROING_STATUSES` and `STAFFING_EXCLUDED_STATUSES`. Overtime is untouched: a quit-marked agent's non-cancelled OT still counts, exactly as before. **Both halves of this rule shipped broken and were fixed in two later commits — see item 76.** Tests: 585/585 (14 new).

76. **Both halves of the Staffing Calculator's Quit/Baja exclusion were broken; fixed in two commits (`6fc3ed9`, then `5d8c2e4`).** The feature (`4092f1b`) exists because supervisors mark an agent's adherence cell `Quit` or `Baja` days or weeks before the formal separation is processed — until it is, the agent is still `status='active'`, so Scheduled Staff kept counting them as coverage. The reported symptom: an agent marked `Baja` for **every day of a week** was still counted, and the popover listed him in the **counted** column wearing a Baja tag.

**Why it survived its own test suite.** All 14 tests written with `4092f1b` marked a **single day**, where the earliest and the latest mark are the same date. The suite literally could not distinguish correct code from broken code. Anyone touching this should assume the multi-day case is the one that matters.

**Fix 1 (`6fc3ed9`) — a day literally coded Quit/Baja is now excluded on its own.** `Quit`/`Baja` are deliberately absent from `STAFFING_EXCLUDED_STATUSES` (they must stay neutral for pay, bonus and Cost of Schedule, and they need *forward* stickiness rather than same-day-only), which left `_place` with **no rule at all for a day that is literally marked**. The only thing that could exclude such a day was `_build_quit_mark_map`'s cutoff — and that map resolves **one** date per agent, the latest mark, so it cannot speak for a whole run. Marked Mon–Sun, the cutoff became Sunday and Mon–Sat fell through and counted. **Marking more days excluded fewer.** A new branch in `_place`, sitting after the `STAFFING_EXCLUDED_STATUSES` check, now excludes any day whose own status is in `SEPARATION_MARK_STATUSES`.

**The literal-day rule and the mark map are two separate rules and both have to exist — do not merge them.** They answer different questions. The literal rule covers **the run itself**: the supervisor typed "gone" on these specific days, so those days are settled facts and need no inference. The map covers **everything after the run**, extrapolating into later weeks that hold no adherence data at all — which is the whole reason the feature is not just a `STAFFING_EXCLUDED_STATUSES` membership. Two consequences worth stating plainly:
  - **`_build_quit_mark_map` is unchanged, and its latest-mark rule is correct.** It was tempting to "fix" this by switching the map to the *earliest* mark, and that was considered and rejected: it works, but it widens retroactively, so one stray `Baja` typed months ago and never cleaned up would drag the cutoff back with it and erase the agent from every historical week in between. The latest mark is the tightest correct bound for forward extrapolation. The bug was never that the map picked the wrong date.
  - **Marking more days can now only ever exclude more days.** The inversion is structurally impossible rather than merely corrected, because each marked day now carries its own exclusion instead of depending on where the run's cutoff lands.

Costs **zero extra queries** — `adherence_status_by_agent_date` is already built for the whole visible week and reused. Keeping the rules separate also means the popover names **each day's own status** in a mixed Quit/Baja run, instead of stamping one cutoff status across all of them. The `exclude=True` gate is preserved, so a quit-marked agent's approved OT still counts as coverage, exactly as before. Known and accepted: if a supervisor marks Mon, Tue, *skips* Wed, then Thu, the unmarked Wed still counts — consistent with the feature's own "anything missing or ambiguous falls through to counting the agent" principle.

**Fix 2 (`5d8c2e4`) — reinstatement now requires real evidence of presence.** The map decides whether a mark still stands by comparing it against the agent's latest "real activity", and that check counted **any** non-mark `AdherenceRecord` as activity. That included the blank, zero-hour row written by `adherence.views._zero_missing_scheduled` on every Five9 daily upload and re-match, for every active agent who was scheduled that day but absent from the file. One clause added to the activity query: `Q(actual_hours__gt=0) | ~Q(status='')`.

**Why a blank zero-hour row is evidence of ABSENCE, not presence — this is the part a future session would otherwise undo.** That row exists precisely *because* the agent did not appear in the Five9 file when they were scheduled to. Its entire meaning is "did not show up". Treating it as proof the agent is still working is not a conservative fail-safe, it reads the signal backwards. And because the upload writes it **every single day**, it out-dated the mark continuously — switching the forward exclusion off for the current and future weeks for essentially every marked agent, since a marked-but-not-yet-separated agent is still `status='active'` and still on their template, which is exactly the population the zero-fill targets. The feature was close to permanently disabled for the case it exists to handle. Three details are load-bearing:
  - **A typed status with zero hours still reinstates** (e.g. `Absent`, 0 h). A human actively typed that, so the agent is still being tracked; this is not the artifact. A test pins it, so the rule cannot be collapsed to `actual_hours > 0` alone — which would also silently break the pre-existing `P`-restores-the-agent test.
  - **`actual_hours` is nullable and SQL three-valued logic handles it correctly.** `NULL > 0` is not true, so a blank NULL-hours row is excluded, while a typed status still reinstates through the second half of the clause.
  - **The filter must stay BEFORE `.values()/.annotate()`.** Moved after, it becomes a `HAVING` on the aggregate and silently stops working.

**`_zero_missing_scheduled` is deliberately NOT touched.** Making it write a status would corrupt the adherence grid, bonus math and NR accounting for what is purely a Staffing Calculator concern. The reader is the right place to fix a reader's misreading.

**This makes Quit and Baja exclusions fire in cases where they previously did not. That is the intended correction, not a side effect** — agents who had been marked as gone were still being counted as coverage. Expect agents to start disappearing from Scheduled Staff who did not before. **No status set membership changed** in either commit: `Quit` and `Baja` remain absent from all five accounting sets (`BONUS_QUALIFYING`, `BONUS_DISQUALIFYING`, `COS_INCLUDE_STATUSES`, `SCHED_HOURS_ZEROING_STATUSES`, `STAFFING_EXCLUDED_STATUSES`), and **no bonus, Cost of Schedule, payroll or overtime behavior changed**. Staffing Calculator only.

**How it was verified beyond the suite.** All 9 new tests are multi-day and each was written and run against its pre-fix commit first. **7 of the 9 failed there**, reproducing the bugs — the Phase 1 failures included the counted list literally returning `{'name': ..., 'status': 'Baja'}`, the reported symptom verbatim. The 2 that passed pre-fix are named as regression guards rather than repros: a whole week marked still excluding the *following* week (forward stickiness already worked, and the obvious wrong fix is to weaken it to make the marked days work), and 0.25 h still reinstating (pins the `> 0` edge). The most valuable test calls the **real** `_zero_missing_scheduled` rather than hand-rolling a row, and asserts the artifact row exists before asserting the count — so it proves the restore came from production code and couples the writer to the reader, which is exactly the drift that caused this. Tests: 585 → 590 → 594.
